# SourceMultiplayerNetworking
```
服务器:
    数据压缩
    延迟补偿
客户端:
    执行预测
    插值
```
## 基本网络
```
tick(始终周期)
默认步长：15ms
每秒 66.666..个tick

服务器在每个tick 之间
    1.会检测游戏规则
    2.更新所有物体状态
    3.世界状态快照
    4.更新客户端状态



客户端运行和服务相同的tick熟虑进行设备采样
    1.当前输入设备的快照

    note: 客户端并不会每个tick 都发送 会每秒发送30次的速率
    这有可能一条数据发送两个或更多用户输入



游戏数据可以增加压缩来减少网络负担
服务器并不会发送整个世界的快照,而是发送和上一次变化(增量数据)

服务器和客户端每发送一个数据都会加上ack 来检测数据是否丢包

服务器保存的完整快照 只有在游戏的开始的时候或者客户端连续数秒受到严重丢包时才会发送,也可以实现一个接口 客户端主动请求完整快照




客户端响应性
  客户端输入 --> 服务器---->客户端执行
  这段时候被称为延迟

  解决该问题:
    1.预测和补偿机制



实体插值
1.
  例如 obj 接收到 位置修改 ojb.position = new_position
  这样看起来回卡顿 从A直接瞬移到B

怎样解决:
    每秒发送20个快照 1000/20 = 50ms

    客户端收到快照位于 tick 344(10.30)
    当前客户端事件 10.32

    渲染时间=客户端时间-100ms=10.22秒

    渲染器永远回放到100ms 之前的状态用已知快照按比例插值



输入预测
    玩家从操作游戏到收到服务器发送的操作命令状态更新这个叫做延迟
    延迟 = 客户端时间 - 服务器时间

解决
  本地输入 不等待服务返回执行命令 而是立即执行命令

  客户端立即运行到新位置 而此时服务还认为它是旧位置

  

  预测与纠正:
     服务器我们认为始终是正确的,如果客户端预测的位置和服务器返回的位置有误,则客户端需要纠正自身

    1.立即纠正:肯造成视图无规律跳动移动
    2.短时间逐步纠正



补偿机制
   
   命令执行时间 = 当前服务器时间 - 数据包延迟 - 客户端视图插值


```
