## 算法基础
### Paxos算法
```
描述
在Paxos 系统中将节点划分诶Propser(提议者) Acceptor(接收者) 和 Learner(学习者)
note:每个节点可以身兼数职


三个阶段:
1.Prepare 准备阶段
  Proposer 向多个Acceptor 发送 Propose Promise
  Acceptor 收到Propose 请求进行Promise
2.Accept 接受阶段
    Proposer收到多数Acceptor 承诺后向Acceptor发出Propse
    Acceptor 接收到Propse 请求惊醒Accept 处理
3.Learn 学习阶段
  Proposer 将形成的决议发送给所有的Learnes


```

### ZAB 协议
```
Paxos 算法的改进算法
只有Leader 作为 Propser(提议者) 提案
模式:消息广播，崩溃恢复


zxid 全局事务id

leader
  fllower1 msg queue
  fllower2 msg queue 



leader zxid 向follower 队列放入一个事务信息 事务信息按顺序发送给对应的folloer

folloer 收到事务zxid 和 需要做的事情 返回 ack

leader 接收到超过半数 ack ,先将自己commit在向follower队列放入commit 消息,commit 消息
发送给follower follower 接收到消息commit信息修改提交上一次事务



崩溃恢复
1.发送完zxid 信息 还没有接收到 ack leader 宕机

2.发送完zxid 接收到 ack 超过半数 还没有发送commit 信息宕机


ZAB协议崩溃恢复必须满足以下两个要求
1.已经被Leader 提交的提案follower 必须执行

2.丢弃已经被Leader提出但是未被提交的提案
  leader 接收到client 提案 还未发送



leader 宕机 选举新leader条件
1.新选出来的leader 不能包含未提交的提案
   老leader的提案 收到 并且 ack

2.新选出来的Leader 必须含有最大zxid



新选出来的leader 会将上一任leader 未处理的完的提案全部处理完,follower 只有处理完对应的提案的fllower,
leader 才会将follower假如到真正可用的Folloer列表中


```

### CAP 理论
```
C:一致性
多个副本保证一致性,当一个系统在数据一致性的情况下更新了数据已经保证数据一致性
A:可用性
系统提供的服务必须一致处于可用状态,用户每一次操作必须在有限的时间返回结果
P:分区容错性



ZK保证的是CP

ZK不能保证每次请求的可用性
Leader 选举的时候集群是不可用的(LOOKING)

```
